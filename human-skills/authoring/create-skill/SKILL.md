# Human Skillを作る

## こんなとき

自分の経験、ノウハウ、練習法、仕事のコツ、判断基準、メモなどを、他の人も再利用できるHuman Skillとして残したいときに使います。

単なる説明文や短いTipsではなく、読んだ人が新しい見方、判断基準、具体的なやり方を身につけられる内容にしたい場合に向いています。

## どうする

最初に、このSkillを読んだ人が何を理解し、どんな場面で何を変えられるようになるのかを決めます。「文章を書く」のように広すぎる場合は、「情報量の多い説明を、意味を落とさず読みやすく整理する」のように、独立して学べる単位まで狭めます。ただし、細かく分けすぎて一つ一つが薄いTipsにならないようにします。

内容には、単なる結論だけでなく、その結論を使えるようになるための中身を持たせます。題材に応じて、次の要素を組み合わせます。

- なぜその考え方や方法が有効なのか
- 何を観察し、何を基準に判断するのか
- 実際にどう進めるのか
- 状況によって判断が変わる条件
- 典型的な失敗と、その失敗が起こる理由
- うまくいかなかったときに何を見直すか
- 良い例と悪い例、または境界例
- 他の場面へ応用するときに何を残し、何を変えるか

「努力する」「よく考える」「自分らしくする」「必要に応じて調整する」のような、読者が読む前から知っている一般論だけで終わらせません。その助言が具体的に何を意味するのか、どのような状況では成立しないのか、判断を変える観察事実は何かまで掘り下げます。

よいSkillは、読み終えたあとに読者の頭の中へ新しい判断装置が一つ増えるような内容です。少なくとも「何を見ればよいか」「なぜそうするのか」「どこでやり方を変えるか」のいずれかについて、読む前より具体的に答えられる状態を目指します。

具体例は飾りではなく、原則を理解するために使います。例を出す場合は、その例のどこが重要なのかも分かるようにします。反対に、例を一つ暗記しないと使えないSkillにはせず、別の状況にも移せる形で原則を言語化します。

`## こんなとき` には、読者が自分の状況と照合できる実際の困りごとや目的を書きます。専門用語だけでなく、読者が検索しそうな日常語や言い換えも自然に含めます。

`## どうする` では、内容を段落、箇条書き、必要な場合だけ番号付きリストで整理します。この区画の中で `###` などの追加見出しは使いません。長い内容も、小見出しを増やすのではなく、話題ごとに段落を分け、必要なら短い箇条書きで構造化します。

`## 補足` は必須ではありませんが、適用範囲、注意点、例外、誤解しやすい点など、本文を使ううえで重要な情報がある場合に使います。ここでも追加見出しは使いません。

Markdownでは、見出しの直後、段落と段落の間、本文と箇条書きの境界に空行を入れます。1文ごとに機械的に改行せず、同じ話題は自然な段落としてまとめます。一方で、異なる論点を巨大な1段落へ詰め込みません。

外部から新しく作るHuman Skillでは、`id` と `author` を勝手に生成しません。Human Skillsへimportするときに、Skill IDとauthorはサービス側で確定します。既存のexport済みSkillを編集する場合だけ、そこに含まれている有効な `id` と `author` を保持します。

完成前に、次を確認します。

- 読む前には分からなかった具体的な学びがあるか
- 単なる常識や標語を長く言い換えただけになっていないか
- 結論だけでなく、判断の根拠や仕組みまで理解できるか
- 少なくとも一つは具体的な適用場面を想像できるか
- 例外や失敗条件が重要な内容なら、それが書かれているか
- 人物名、ブランド名、元資料を知らなくてもSkill単体で使えるか

これらを満たせない場合は、公開用Skillにせず、内容を追加するか、他の近いSkill候補と統合します。

## 補足

Human Skillは短ければよいわけではありません。短くても十分な学びがあるなら短くて構いませんが、読みやすさを理由に重要な理由、判断基準、失敗条件、具体例まで削らないでください。

一方で、情報量を増やすためだけの背景説明や重複も不要です。目標は長文化ではなく、「そのSkillを学ぶ意味がある密度」にすることです。
